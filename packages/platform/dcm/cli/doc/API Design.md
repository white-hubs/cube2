# 申明式配置模块Provider API设计


## 0. 背景与基础原则
本设计旨在解决命令式操作的出错处理与多路径升级协调困难问题, 借鉴现代运维环境中的申明式配置管理思想, 实现模块化应用系统的配置的声明式操作。

申明式配置也有其自身的短板, 对于一些用命令方式很容易做的升级动作难于描述, 同时由于参与操作的随身都是配置的全貌快照, 进行动态操作描述会存在一定困难, 同时对于高吞吐大负荷系统进行在线操作也有一些负面影响。 

但基于我们目前的业务现实，在相当时间范围内都是合适的。 对于需要特别进行的动态操作， 我们将转向使用其他运维手段与配置式操作相结合进行支持。

以下是我们的实现中需要遵循的基本原则。
1. 模块化, 应用模块提供本模块自身的能力与需求
2. 配置的一体化与版本化 人类友好的语义化申明式配置, 方便随时查看配置需求的全貌

本文件主要描述提供配置能力的模块需要实现的接口。

## 1. 模块化设计
原则上模块自行提供实现, 避免不必要的知识泄漏。 
模块暴露自身提供的配置类型，和对应的配置规格版本信息 (每一种配置类型都允许有不同的参数 )。

## 2. API 类型
1. 静态配置获取类
2. 动态配置获取类
3. 配置差异获取
4. 配置差异应用

##  3. 配置类型


| 分类维度  | 分类选项      | 分类样例           | 分类说明                                     | 识别方案        | 
|-------|-----------|----------------|------------------------------------------|-------------| 
| 配置获取  | 动态、静态     | 动态             | 动态来源于API获取, 静态来源于预先获取的资源解析               | 调用者负责       |
| 应用范围  | 租户级/系统级   | 系统级            | 租户级配置影响基于租户,实际可能发生在与应用绑定的全部租户上,系统级配置影响所有系统 | 协同解决(调用参数等) | 
| 项目适应性 | 特定部署/所有版本 | 成农批项目          | 特定部署指特定部署环境, 如特定项目。 所有版本指通用设置            | 调用者管理       |
| 环境适应性 | 特定环境/所有环境 | Win64, Linux32 | 特定环境指特定环境, 如特定系统平台，特定数据库，特定网络等。 所有环境指通用设置 | 协同解决(调用参数)  | 

另需要明确，无论是什么样的分类维度下的配置， 都需要考虑发生在全新系统和升级迁移两种情况下的兼容性。这也是声明式配置本身的精髓所在，但对于
实现者有更高的要求, 不过申明式配置本身有它自己实现范式, 基于相应的范式进行实现即可（目前我们通过API 类型区分了支持声明式配置的标准动作，
以指引大家的实际实现工作。）

配置描述语言需要定义清晰如何对这些配置项目的分类维度进行区分；而API的实现需要能和
调用者协调以明确出来调用的场景是哪一类情况 （因为配置可能是统一、集中提供的， 而应用场景是动态的，变化的。）

## 4. API 端点规格定义

定义服务访问基地址为变量baseurl
使用Post传递数据, mime type支持application/json和application/yaml, 响应消息体格式也同时支持json与yaml.
### 公共定义的QueryParam
| 参数 | 数据类型 | 含义                                                                                                          |  备注 |
|-------|------|-------------------------------------------------------------------------------------------------------------|------------------------------------------|
| runtime | 布尔型  | 是否应用与运行时数据. <br/>True 获取当前运行时的配置数据(通常是从数据库中抽取的)<br/> False 获取代码静态资源定义的配置数据 缺省: False                        |  |
| tenant | 字符串  | tenantId(通用于应用和获取配置). 包含此参数意味着返回适用于特定租户的定义(包含通用所有租户与该特定租户的配置)。指定一个不存在的租户而又指定获取运行时配置时, 返回空数据。 | |
| system | 布尔   | 是否处理系统级(租户无关)配置. 指定了有效tenant后, 默认为False.                                                                    | | 

### 抽取配置与(本模块内部定义的)配置差异
```http request
GET ${baseurl}/dcm/config
Accept: application/json
```

获取制定服务上的配置.  支持静态配置获取, 运行时配置获取, 静态配置与运行时配置差异的获取。
包含diff参数时, 返回当前runtime 和内置资源间的diff. 指定了diff后 runtime参数无效, tenant 与 system仍然有效, diff包含由现有配置过渡到预期配置时需要调整的全部项目. 该diff模式下, 对于超出配置申明的部分不做处理。
不含diff参数时, 依据runtime参数, tenant参数, system 参数返回指定的配置. 
指定runtime = False时, 允许返回无视tenant参数与system参数. 

获取配置时, 返回内容格式同申明式配置中的完整格式
获取配置差异时, 同申明式配置语法, 

### 比对运行时配置与指定配置申明间的差异

本方法生成由现有运行时配置变换到指定配置申明间需要进行的配置变更项目的申明状态。本方法支持tenant/system等参数指定比对的内容范围.

```http request 
POST ${baseurl}/dcm/config/diff
Content-Type: application/json
Accept: application/json
```
* 支持tenant/system 作为query param.
* 内容schema: 
示例使用yaml表述如下: 
```yaml
isPartialMode: True # 需求为部分模式, 仅考虑提供的项目的新增/修改和删除, 缺省为True, 指定为False时, 需求中未指定的部分均需要删除.
requirements:
  - configType: DictType  # 需要的配置能力类型
    version: 1.0 # 配置能力描述使用的版本号
    # 是否本配置项必选(必须配置成功, 失败则终止配置报错) 缺省为True
    isMandatory: True
    # 未指定tenants时即系统配置.
    # 匿名参数是数组, 数组元素的类型依赖于特定的模块支持的能力, 允许是数组,对象.
    vargs: ["TypeA", "TypeB"]  
  - configType: DictEntry
    isMandatory: True
    # 从DCM 1.0.3 开始, 支持整体需求的 isPartialMode = True的情况下，为指定的一种具体配置类型指定为非PartialMode
    # 由于同个configtype 可能会被拆分为多个不同的RCI, 无法统一逻辑一致地处理单个RCI 被指定为非PartialMode(即某一个是全
    # 量更新，而其他的同类型RCI 是增量更新，尽管这可能是某些人心目中的一个理想状况）， 我们当前制定如下策略：即同一个Requirement当中
    # 同一个ConfigType下的不同RCI, 有任意一个被指定为非PartialMode, 则该configtype 全部被指定为非PartialMode。
    # isPartial: True, 将会对该类型执行全量更新。    
    tenants: all  # 租户级, 适用于所有租户; 用于指定租户时可以指定逗号分割的租户id列表, 用于项目级配置文件. 
    kwargs:  # 命名参数, 可以为空
      dictType: TypeA  # dictType 是能力提供方提供的配置命令的参数
    vargs: ["item1", "item2", "item3"] # 匿名参数, 实际是否可以考虑把匿名参数作为命名参数的特例?
  - configType: DictEntry
    isMandatory: False
    isRemoval: True # 提供这种支持, 仅用于确保partialmode 逻辑的完整性, 应该尽量避免; 因为删除带来的冲突无法以可接受的方式自动消解.
    kwargs: 
      dictType: TypeB  # dictType 是能力提供方提供的配置命令的参数
    vargs: ["item1", "item2", "item3"]
```

### 应用申明式配置
使当前模块的运行时配置达到指定的申明式配置状态。

请求定义如下：
```http request 
POST ${baseurl}/dcm/config/apply
Content-Type: application/json
Accept: application/json

```
该请求有两种形态，他们都支持tenant/system等参数以指定执行的内容范围.
#### 1. 通用形态: 应用外部提供的配置申明
发送内容示例如下:
```json
{
  "provider": "DICT",
  "isPartialMode": true,
  "useBuiltinConfig": false,
  "requirements": [
    {
      "configType": "DictType",
      "version": "1.0",
      "isMandatory": true,
      "vargs": ["TypeA", "TypeB"]
    }
  ]
}
```
#### 2. 特殊形态: 应用模块内置的对本模块的配置申明
作为 GET /dcm/config?diff 的应用, 适用于对本模块的初始化动作.
发送的post body 内容为:
```json
{
  "isPartialMode": true,
  "useBuiltinConfig": true
}
```
如果模块不包含内置的对本模块的配置需求, 始终返回成功.
