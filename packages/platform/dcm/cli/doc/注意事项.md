# 注意事项

本文件将逐步汇总目前DCM 使用中的一些需要注意的事项。 

DCM 为提供配置的最终状态提供了一种易于进行版本配置管理的的方式。但由于设计和使用理念上的限制，目前DCM 的配置管理功能仍存在以下一些受限情况

## 关于全量更新（NON PARTIAL MODE）与删除

在DCM当中， 删除操作可能会来源于显式指定的删除型RCI, 或被要求进行全量更新时目标状态中不存在的配置项。
全量更新与删除，对于配置而言始终是一个高风险动作。
为此，尽管在dcm的请求规格中有关于删除与全量更的的规范，但实际是否允许执行全量更新和删除动作，取决于DCM Server所运行的server的两个系统属性：

| 属性 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| dcm.server.enable-non-partial-mode | 布尔 | false | 是否允许执行全量更新动作 |
| dcm.server.enable-removal | 布尔 | false | 是否允许执行删除动作 |

默认情况下，DCM Server将不允许执行全量更新和删除动作。
但在特定情况下（通常是测试或初始化系统时，或临时性启动一些实例）， 允许执行全量更新，或不允许全量更新，但允许显式被指定为删除的操作被执行。

## 关于DCM 请求中全量更新模式指定
默认情况下DcmRequirement isPartialMode=True, 仅允许增量更新，此时允许部分的RCI被指定为isRemoval 而带来删除操作。

全量更新指定的最小单位是一个配置类型，将不会支持更小的配置单位。但由于一个配置类型允许被拆分成为多个RCI, 目前逻辑是同一个配置类型下，任意的RCI被指定为
全量模式，则该Requirement中相同作为范围内：同一个config type + 系统或租户的所有RCI 合并成为当前作用域的全量。

如果对于应用变更实际会带来的影响不明确，请先通过Diff请求获取当前系统判定的差异和将执行的变更。

## 数据库约束带来的更新失败
当DCM Server在数据库中执行更新操作时，如果出现任何数据库约束或逻辑约束错误，将造成对应的ConfigType的处理失败。
由于实际的约束情况千差万别，DCM自身无法以有效的手段完全解决，这可能会导致同一份配置，无法一次性应用成功。

目前DCM 采取的策略是尽最大努力执行，但如果在应用差异阶段出现任何项目的错误，都将在客户端报告为出错。（但实际可能仍然已经执行了部分更新）
为此建议：
1. 反复多次尝试以相同的数据加以apply, 直到不再有新的更新或错误返回为此。
2. 如果始终存在有错误报告，检查报告内容，尝试分析和找到出错原因（各DCM实现者需要尽量在出错误信息中包含有用的分析信息）加以修正后处理

## 常见造成始终待更新项目但未报错的情况
1. dcm entity的getId 方法与DcmHelper的getBizKey方法生成内容不一致
2. 记录实体更新方法实现问题
3. 原数据库中相同的key的实体记录有多条，当前设计不允许更新全部记录，需要核实dcm 后台日志, 可搜索”multiple entry with same key“ 字样。
4. 其他，待补充更新。
